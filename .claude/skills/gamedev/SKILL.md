# gamedev — шлюз цілісності гри

Дистильовано з дослідження «Godot-інді студія з ШІ-командою» (2026-11-05, https://claude.ai/artifact/J5kSt6HmHX7qqDGx8FhB28) і з власних провалів цієї кодбази. Головна теза: неправильні механіки, керування й UI **не лікуються кращою генерацією коду**. Їх лікують ворота якості ДО арту, докази замість «виглядає робочим» і живі люди на плейтесті. Агент готує й перевіряє, а рішення ухвалює власник.

Цей скіл — **вхідна точка** процесу; сам процес (принципи P1–P10, цикл поставки, ролі, ритми, метрики) — `docs/process/README.md`. Метод геймдизайну й реєстр D/M — `docs/process/game-design.md`. Ролі-агенти — `.claude/agents/` (`designer`, `developer`, `integrity`, `qa-adversary`, `fresh-eyes`).

## Автопілот (як це виглядає для власника)
Власник лише каже, чого хоче, тисне кнопки на питання й мерджить PR. Ролі не називає, файлів процесу не редагує. На будь-який ігровий запит ти **сам** ведеш цикл: тріаж §2 → стовп (§1; нема — питання кнопками) → спека з `specs/_TEMPLATE.md` (агент `designer`) → грейбокс/код із доказами → тести від REQ (`qa-adversary`) → кадри + тест Ніколая (`fresh-eyes`) → вердикт воріт (`integrity`) → PR. Власнику віддаєш **PR + ≤ 4 питання з варіантами** (`AskUserQuestion`; пакет рішень — `/decide`). Його правки результату сам пишеш у `docs/process/rework-log.md`.

## 0. Ролі й межі (читай першим)
- **Власник вирішує:** ядро й стовпи, scope, модель вводу, політику ШІ-арту, зміни балансу (міцність інструментів, ціни, складність). Агент пропонує чернетку з варіантами й **не ухвалює** їх сам.
- **Агент у ролі PM-цілісності** перевіряє зв'язки, яких не видно зсередини однієї задачі: механіка ↔ керування ↔ UI ↔ перші 60 секунд ↔ тексти. PM не пише правила гри, а виносить вердикти воріт.
- **Агент у ролі розробника** закриває задачу лише з доказом (§3) і не змінює правила гри мимохідь.
- **Агент не обирає scope.** Кожна нова система мусить посилатися на стовп (§1). Якщо стовпа нема — це питання власнику, а не привід зробити «бо цікаво». Прецедент: мережа, ферми, режисер і net-спайк з'явились у прототипі Фази 0, і не всі їх просив власник.

## 1. Ядро і стовпи (ворота 1)
Файл правди — `docs/design/pillars.md` (статус `draft` → `approved` ставить лише власник, OD-1). Поки статус не `approved`, **кожна задача на нову механіку починається з питання власнику**. Чернетка до затвердження (НЕ затверджено):
- **Ядро:** «Виживи один на справжній карті свого міста: добувай, будуй укриття й ховайся від машин — світ є функцією координат».
- **Стовпи:**
  1. справжнє місце (координати = світ);
  2. тіло і клімат вирішують (глибокий сим одного героя);
  3. машини полюють (загроза, яку читаєш і обходиш).

Фіча, що не підсилює жодного стовпа, отримує статус «заморожено», а не «зроблено пізніше».

## 2. Тріаж запиту → маршрут
| Запит | Маршрут |
|---|---|
| Нова механіка або система | §4-анкета → ворота 0–1 → спека `specs/NNNN-*.md` (Specify / Дизайн / Перевірка / Ризики) → грейбокс без арту → тести + FTUE-замір → лише тоді арт (`/gen-art`) |
| Керування, «незручно» | Ворота 0 і 2: виміряй відгук на ввід, перевір матрицю вводу; полірування — після рішення про модель вводу |
| UI/HUD, «погано виглядає» | `/godot-game-uiux-designer` + обов'язковий тест Ніколая (§5) як вихідні ворота |
| Арт | `/gen-art`, але тільки для механік, що пройшли ворота 0–1 (інакше арт перемальовується) |
| Баг | Відтвори з тим самим seed і `--fixed-fps` до й після, тест-регресія, `world_hash` не зсувається без причини |
| Баланс | Цифри + симуляція (бот або тест) → рішення власника; без рішення — не міняти |
| Онбординг, «перша хвилина» | Ворота 4: FTUE-метрики (§6), один вибір за раз |
| «Чи це цікаво», плейтест | Ворота 5: протокол для людей (§7); ШІ тут не суддя |
| Реліз, демо, Steam | Ворота 2 і 6, CI-артефакти (APK / web); Steam — не цільова (OD-4), платформа — OD-9; розкриття ШІ-арту за її правилами (F9) |

## 3. Правило доказу: без артефакту нема «готово»
Кожне «зроблено» в повідомленні чи PR несе щонайменше одне з цього, а для UX — усе:
- **лог тестів**: `test.cmd` / сьюти Godot + `npm test` + `npm run lint` + `gdlint`, без ObjectDB-ліків;
- **кадр**: `xvfb-run -a -s "-screen 0 1600x720x24" godot --path godot res://newhud.tscn -- newhud shot [inv|bag|death|spawn|fx] [touch scale=1.68]`; до/після для будь-якої видимої зміни;
- **replay/детермінізм**: twin-хеш (`run_determinism_tests`) або `world_hash` до/після;
- **тест Ніколая** (§5) для будь-якої зміни, яку бачить гравець.

Механічно це тримає PR-гейт (`.github/workflows/process.yml` → `tools/process/check-pr.mjs`): без «Доказів» для продуктових файлів, без кадру для видимого чи без REQ/OD/spec для зміни правил гри PR червоний.

Зелені тести, написані тим самим агентом, — **не доказ досвіду гравця**. Прецедент: ~1100 тестів не впіймали, що екран смерті бреше про торбу, що «5/10» в цілі означає номер кроку, і що тексти накладаються (F3).

## 4. Анкета нової механіки (до першого рядка коду)
1. Яке **одне речення** описує механіку для гравця? Якому **стовпу** вона служить?
2. Чи можна її **навчити без тексту**? Якщо ні, механіка повертається на доопрацювання.
3. **Ввід:** як вона працює на дотику (кнопка дії, радіальне меню, хотбар)? Фаза 0 — лише телефон (OD-2); КБМ — інструмент розробки, не вимога. Чи не потребує вона нового глобального елемента HUD?
4. **Канал фідбеку:** котрий із контракту каналів (загроза / відмова над героєм / ціль дії / фід / підказка) і **який стан HUD** (світ / будівництво / бій / інвентар / огляд)?
5. **Що вона ПРИБИРАЄ?** UI росте додаванням, тому кожна фіча має замінити, а не лише додати. Ліміт телефона — ≤ 16 постійних елементів.
6. **Тексти:** які наявні рядки (смерть, цілі, підказки, фід) стають неправдою після неї? Знайди їх grep-ом і онови в тому ж PR.
7. **Детермінізм:** лише seeded RNG, стан у `serialize_region`, прапор OFF = байт-у-байт (патерн `use_catalog`/`use_inventory`).
8. **Як виміряємо, що вона працює для гравця** (FTUE-метрика, кадр, плейтест-задача)?

## 5. Тест Ніколая (ворота 3) — незалежне око
Мета: хибні афорданси й нерозшифровані сигнали. Модель, яка вирішила, що декоративна жаба інтерактивна, віщує, що так вирішить і частина гравців. Запускай **окремим агентом без контексту проєкту** — агент `fresh-eyes` (`.claude/agents/fresh-eyes.md`, інструмент лише Read; його не можна заякорити моїми висновками), дай лише шляхи до кадрів:
> «Ти вперше бачиш ці скриншоти незнайомої гри. Не читай коду. Для кожного кадру: (a) що, на твою думку, інтерактивне і що воно робить, що виглядає інтерактивним, але є декором; (b) що екран обіцяє — що робити далі; (c) які іконки чи числа не розшифровуєш; (d) куди йде погляд 1-2-3; (e) що найбільше плутає. Наприкінці — топ-5 проблем розуміння. Буквально, що бачиш, а не що задумав дизайнер.»

Мінімальний набір кадрів: спавн, світ (десктоп), світ (телефон), відкрита панель, смерть, плюс кадр зміненого екрана. **Пройдено**, коли немає хибних афордансів, кожне число на HUD розшифроване (підписом, підказкою або першим запуском), а «що далі» названо правильно. Перший прогін (2026-11-05) провалився: медальйони читались як кнопки, робот — не як загроза, ✖/🗑 — як руйнівні дії, «є 1» — як «ε 1».

**Журнал прогонів (2026-11-05, 3 цикли «тест → правка → тест»):**
- **Що закрили:** спавн — одна залита кнопка «Грати · Київ», інше під «Інше місце ▾»; смерть — причина + дні + торба «позначена на мапі», без роду; намір ворога словами («ламає стіну», «удар −N»); підписи медальйонів (назви перші 2 дні, далі лише слово тривоги); тепло без «11°»; їжа тривожить лише коли справді мало; «бракує» словами («⚙ брухт ×8»); флеш над героєм; ✕ в інвентарі; кнопка дії сама стає «Будувати», коли в руці будівля, з привидом у рамці.
- **Уроки:**
  1. Кожен прогін знаходить нове — **3 цикли мінімум**, бо виправлення відкриває наступний шар.
  2. **Артефакти підготовки кадру** (`_build_demo_base`: застарілий флеш крафту, «виконано 5 цілей» на 1-му дні) тест сприймає як гру — стадіюй чесно або відфільтровуй.
  3. **Ієрархія тривог** важить більше за кількість сигналів: найгучніший червоний мусить бути найбільшою загрозою.
  4. Два однакові числа різного змісту (−19°C надворі та 11° відчуття) — завжди загадка: лиши одне, друге — словом.
- **Ще відкрито:** загроза біля бази без тривоги-банера, і на телефоні табличку робота ховають медальйони; читабельність мапи (руда/камінь, турель/пастка — арт); подвійний хотбар в інвентарі (за задумом Minecraft, але плутає); фід «обери проєкт», коли «Дослідження» згорнуте.

## 6. FTUE — перші 60 секунд (ворота 4)
- **Один вибір за раз.** Спавн-екран — одна головна дія («▶ Грати · <місто>»), решта під «Інше місце…».
- **Метрики** (детермінований сим робить їх вимірюваними; цільовий інструмент — headless FTUE-бот через verbs):
  - сим-секунди й кількість дій до першого збору, до багаття, до укриття;
  - відсів між цілями `goals.gd`;
  - кількість постійних елементів HUD;
  - попарні перетини видимих Label.
- **Цілі:**
  - перша осмислена дія < 30 с;
  - багаття < 60 с;
  - 0 перетинів текстів;
  - ціль вказує на місце у світі (маркер або пульс слота), а не лише в куті.
- **Смерть навчає:** причина + день + що робити інакше + де торба (spec 0009). Звертання без граматичного роду.

## 7. Людський плейтест (ворота 5) і демо (ворота 6)
- 3–7 гравців, **мовчки** (не підказувати), 5 задач без інструкцій: висадитись, розпалити багаття, пережити ніч, скрафтити й поставити будівлю, знайти торбу після смерті. Нотувати місця, де людина зупиняється більше ніж на 5 с, і що вона пробує натиснути. Виправлення того ж дня.
- Канали: APK з CI (`android-apk`), web-build (Steam — не цільова, OD-4). Голос гравця важить більше за агентську думку про «цікаво». Ворота 0, 5 і 6 — завжди людські.
- Демо-тест 30 хв незалежним тестером: керування, послідовний арт, навчання, продуктивність.

## 8. Ворота 0 і 2: керування й ввід
- **Ворота 0:** грейбокс, відгук на ввід видно приблизно за 100 мс (анімація, звук, FX), буфер вводу там, де доречно. Нова дія спершу живе без арту.
- **Ворота 2:** уся гра досяжна з **дотику** — Фаза 0 лише телефон (OD-2, 2026-11-05); КБМ лишається для розробки й не є воротами, геймпада немає. Текст ≥ 12 px логічних на цільовому телефоні, < 12 — лише бейджі-числа. Гліфи підказок — під активний пристрій (`Fmt.touchify`).
- **Модель вводу фіксується ДО полірування UI.** Прецедент: будбар → шухляда → кнопка дії → хотбар інвентаря — 4 переробки, бо модель не була зафіксована.

## 10. Відкриті рішення власника
Реєстр — `docs/design/decisions.md` (OD-1 ядро й стовпи · OD-2 модель вводу · OD-3 заморозка scope · OD-4 політика ШІ-арту · OD-5 міцність інструментів · …). Агент додає відкриті рядки з варіантами; закриває лише власник. `npm run process` показує відкриті на старті сесії.
