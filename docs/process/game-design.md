# Геймдизайн: метод і реєстр принципів

> Як ми вирішуємо, ЩО робити, і як перевіряємо дизайн так само суворо, як код. Відповіді для цієї гри — `docs/design/`; тут — метод.
> Реєстр D/M нижче — мірило для рев'ю спек і GDD-дифів (агенти `designer`, `integrity` цитують ID).

## 1. Ієрархія правди

```
Ядро (1 речення)  →  Стовпи (3)  →  Петлі (core / meta)  →  Системи  →  Механіки  →  Контент  →  Арт
     власник           власник          власник + designer      designer     designer+dev    dev       /gen-art
```

- Зміна тече **вниз**. Нижній рівень ніколи мовчки не змінює верхній: механіка, що «не вписується», — це питання власнику про стовп, а не тихе розширення стовпа.
- Кожен елемент нижнього рівня **посилається** на верхній: механіка → петля → стовп. Обірване посилання = кандидат на заморозку (P7).
- Чим нижче рівень, тим дорожча помилка, знайдена пізно (P4): помилку стовпа дешево знайти на папері, дорого — після 300 асетів.

## 2. Ядро і стовпи — якість формулювання

**Ядро** — одне речення, яке гравець сам скаже після 10 хвилин гри. Перевірка: на плейтесті просимо «опиши гру одним реченням» і порівнюємо слова (`playtest.md`, метрика M-core).

**Стовп** — це *досвід*, а не фіча. Добрий стовп:
1. **виключає** — з нього випливає хоча б одне «ні» (інакше він нічого не вирішує);
2. **відчутний** — гравець може його описати, не знаючи терміна;
3. **перевірний** — є плейтест-задача або метрика, що показує, чи він тримається;
4. **незамінний** — прибери його, і гра стане іншою грою.

Три стовпи — стеля, не мінімум. Четвертий стовп зазвичай означає, що один із трьох — фіча.

## 3. Петлі

Петля — ланцюг **дієслів гравця**, що повертається у свій початок із приростом.

- **Core loop** (хвилини): кожне дієслово має ввід, фідбек і наслідок.
- **Meta loop** (сесії/дні): що змушує повернутись завтра.
- Механіка, яка не чіпляється за дієслово петлі, — прикраса; прикраси — після G5.

Тест петлі: *прибери одне дієслово — чи петля розірвалась?* Якщо ні — дієслово зайве.

## 4. Механіка: від питання до спеки

1. **Анкета** — `.claude/skills/gamedev/SKILL.md` §4 (8 питань: одне речення, стовп, навчання без тексту, ввід, канал фідбеку, що прибирає, тексти, детермінізм, метрика). Без відповідей — спеки нема.
2. **Кошторис уваги.** Кожна механіка коштує гравцю: нові дієслова, нові поняття, нові елементи HUD, нові тексти. Пиши кошторис у спеці; бюджет фази — ≤ 1 нове поняття на сесію навчання, HUD ≤ 16 постійних елементів (телефон).
3. **Спека** з `specs/_TEMPLATE.md`: REQ-ID на кожну перевірну вимогу.
4. **Грейбокс (G0)** в окремому git-worktree (`isolation: worktree`): одноразовий код не торкається основного дерева; у main потрапляє лише після вердикту власника «приємно діяти».
5. **Числа балансу** — лише як *пропозиція з доказом* (симуляція/бот/таблиця) → рішення власника (OD-n). Без рішення числа не змінюються.

## 5. Вимоги зі стабільними ID

- Формат: `REQ-<номер спеки>-<n>` (напр. `REQ-0010-03`). Номер **ніколи не перевикористовується і не перенумеровується**; видалена вимога лишається рядком зі статусом `withdrawn`.
- Вимога — одне речення, яке можна перевірити (тест, кадр, метрика або плейтест-задача), з колонкою «Як перевіримо».
- Історії, тести й PR посилаються на ID, а не цитують текст — правка формулювання не ламає зв'язків (TR-registry з Claude Code Game Studios).
- Звіт процесу (`npm run process`) підсвічує нові спеки (≥ 0010) без REQ-ID.

## 6. Рев'ю дизайну як рев'ю коду

Дизайн-документи — Markdown поруч із кодом; їх диф рев'юється за реєстром нижче (практика Luden.io).

- **Хто:** `integrity` (або `designer` на чужій спеці). **Не** автор спеки.
- **Як:** кожна знахідка цитує `D-n`/`M-n`, рядок спеки і пропозицію. Без ID — не знахідка, а смак.
- **Вердикт:** `approve` · `changes` (список) · `owner` (потрібне OD-n).
- Правки після зустрічі можна диктувати голосом як задачу — агент перетворює їх на диф спеки, а не на код.

## 7. Реєстр принципів дизайну (D)

Дистильовано з досліджень і з провалів цього репо (журнал тесту Ніколая, gamedev §5). Додавай нові з підставою.

| ID | Принцип | Перевірка |
|---|---|---|
| D1 | **Один вибір за раз.** Екран має одну головну дію; решта — за розкриттям. | На кадрі одна залита кнопка/одна ціль. |
| D2 | **Навчай без тексту.** Механіка, яку не навчиш світом і фідбеком, повертається на доопрацювання. | Плейтест: гравець робить це без підказки. |
| D3 | **Ціль вказує на світ.** Онбординг показує МІСЦЕ (маркер, пульс слота), а не лише рядок у куті. | Кадр: від цілі до місця дії є візуальний зв'язок. |
| D4 | **Ієрархія тривог.** Найгучніший сигнал — найбільша загроза; тривога звучить лише коли справді треба. | Кадр загрози: найчервоніше = найнебезпечніше. |
| D5 | **Одне число — одне значення.** Два схожі числа різного змісту на екрані — загадка; лиши одне, друге — словом. | Тест Ніколая не питає «що означає N». |
| D6 | **Відгук ≤ 100 мс.** Кожен ввід має видимий/чутний відгук; затримку сповіщає анімація. | G0: замір у грейбоксі. |
| D7 | **Смерть навчає.** Причина + скільки прожив + що робити інакше + де втрачене. | Екран смерті проходить тест Ніколая. |
| D8 | **Чесна система.** Немає субстрату — нема ефекту: payload скидається, не імітується. | Код-рев'ю: жодних фейкових сигналів. |
| D9 | **Одна правда.** Що бачить гравець (оверлей, підказка) = що рахує сим. | Tripwire-тест «одна правда». |
| D10 | **Рідкісна пунктуація.** Сильні події (рейди) рідкі й передбачувані за читанням, а не за таймером. | Сим-тест каденсу; плейтест «чи бачив наближення». |
| D11 | **Віднімай.** Нова фіча замінює щось (елемент HUD, крок, поняття). | Розділ «Що прибрано» у PR/спеці. |
| D12 | **Модель вводу до UI.** Спершу фіксуємо, ЧИМ грають (дотик / КБМ / геймпад), потім малюємо. | OD про модель вводу вирішено до полірування. |
| D13 | **Світ = функція координат.** Будь-яка механіка, що ламає детермінізм від lat/lon, вимагає ADR. | twin-хеш, `world_hash`. |
| D14 | **Без граматичного роду у зверненні.** Тексти не вгадують стать гравця. | grep по рядках UI. |

## 8. Типові помилки (M)

| ID | Помилка | Як виглядає | Протидія |
|---|---|---|---|
| M1 | Занадто складна система | Гравець не може пояснити, що вона робить | D2; кошторис уваги |
| M2 | Забагато інформації на екрані | > 16 постійних елементів, тексти накладаються | D1, D11; FTUE-метрика перетинів |
| M3 | Кілька кроків в одному UI-моменті | «Обери, потім підтверди, потім…» | D1 |
| M4 | Хибний афорданс | Декор читається як кнопка (медальйони-кнопки) | тест Ніколая (G3) |
| M5 | Тексти відстали від механіки | «Усе, що ніс, втрачено» після інвентаря-торби | анкета §4 п.6 (F10) |
| M6 | «Спроєктовано» сприйняте як «скоро буде» | Системи в GDD без рішення про фазу | `docs/design/scope.md` |
| M7 | Переробка вводу після UI | Будбар → шухляда → кнопка дії → хотбар | D12; OD-модель вводу |
| M8 | Механіка без петлі | Система живе, але жодне дієслово гравця її не чіпає | §3 тест петлі |
| M9 | Фіча без стовпа | «Бо цікаво» | P7, PR-гейт PR-3 |
| M10 | Число без підстави | Баланс змінено «на око» | §4 п.5 → OD |

## 9. Що оцінюють лише люди

Агент перевіряє, **що працює**. Люди вирішують, **чи приємно** (G0), **чи зрозуміло з першої хвилини** (G4 — з телеметрією, G5 — очима) і **чи хочеться ще** (G5–G6). Агентні тексти «це цікаво/весело» — не доказ і в PR не пишуться.
